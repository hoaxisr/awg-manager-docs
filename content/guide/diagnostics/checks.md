**Проверки** — автоматическая диагностика всей связки: роутер, DNS клиента и каждый запущенный туннель. Удобно начинать отсюда, когда «что-то не работает», и прикладывать отчёт к issue.

![Вкладка Проверки](/img/guide/diagnostics/checks.png)

## Как запустить

- **Запустить все проверки** — прогон всех групп по очереди (во время работы кнопка показывает текущую фазу, после — меняется на **Запустить ещё раз**). Результаты приходят потоком, по мере готовности.
- **Проверить** у группы — перезапустить только эту группу, не гоняя весь цикл.
- **Шестерёнка** справа — расширенные параметры: тумблер **Включая restart-цикл** (см. [ниже](#restart-цикл)).

Результат каждого теста — зелёный (пройден), жёлтый (предупреждение), красный (ошибка) или серый (пропущен — проверка неприменима), с текстовым пояснением. Группы с проблемами разворачиваются сами, итог — в пилюлях `OK` / `WARN` / `FAIL`.

Проверяются только **запущенные** туннели: AWG-туннели, sing-box-туннели и активные участники подписок. Системные NativeWG- и внешние туннели в проверки не попадают. Если запущенных туннелей нет, пройдут только общие группы.

## Маршрутизация по DNS

Группа «DNS клиента + access policy» проверяет *ваше* устройство — то, с которого открыт awg-manager:

- **Резолв через клиентский DNS** — браузер запрашивает служебное имя `awgm-dnscheck.test`, которое роутер отвечает только на время проверки. Если запрос дошёл до роутера — устройство использует DNS роутера, и DNS-правила на нём сработают. Если нет — устройство ходит в внешний DNS (или DoH/DoT в браузере), и [DNS-маршрутизация](../../dns-routing/) на нём работать не будет. При включённом sing-box проверка пропускается: DNS тогда обрабатывает sing-box.
- **Политика доступа клиента** — в какой политике NDMS находится устройство. Предупреждение, если это не политика по умолчанию.

Рядом показывается IP клиента. Если awg-manager открыт через reverse proxy (например, KeenDNS), группа предупредит, что DNS-проверки в этом случае неактуальны.

## Глобальные

| Проверка | Что проверяет |
|---|---|
| WAN up с gateway | хотя бы одно WAN-подключение поднято и есть маршрут по умолчанию |
| NDMS отвечает | система управления роутером отвечает на запросы |
| Модули AmneziaWG | загружены модули ядра AmneziaWG (пропускается, если прошивка обфусцирует нативно) |
| Расхождение времени с эталоном | часы роутера сверяются с HTTP-заголовком Date нескольких крупных сайтов: больше 60 с — предупреждение, больше 300 с — ошибка (рукопожатия и TLS начинают ломаться) |
| Direct связность | доступ в интернет напрямую, без туннелей и прокси |
| Sing-box runtime | установлен ли и запущен sing-box, его версия и число туннелей |
| Осиротевшие маршруты | маршруты через интерфейсы, которых больше нет (только при полном прогоне) |

## AWG-туннели

Отдельная группа на каждый запущенный туннель:

| Проверка | Что проверяет |
|---|---|
| Резолв endpoint | доменное имя сервера резолвится |
| Ping endpoint | сервер отвечает на ICMP. Нет ответа — только предупреждение: многие VPS закрывают ping, а работает ли сервер, показывает проверка handshake |
| Host route до endpoint | маршрут до сервера установлен в системе через действующий или выбранный WAN-интерфейс (пропускается для NativeWG и на OS 4.x) |
| Handshake свежий (<3 мин) | последнее рукопожатие было не больше 3 минут назад. Ошибка — сервер не отвечает, неверные ключи или параметры обфускации |
| Связность через туннель | запрос к ifconfig.me / icanhazip.com / ip.me строго через интерфейс туннеля; показывает внешний IP. Пропускается, если AllowedIPs туннеля не включают `0.0.0.0/0` |
| Правила iptables | нужные правила файрвола на месте (пропускается для NativeWG) |
| Валидация конфига | в конфиге есть обязательные поля |
| Консистентность state | статус туннеля в awg-manager совпадает с реальным состоянием интерфейса |
| MTU интерфейса | текущий MTU |
| AWG Proxy статус | для NativeWG на прошивках без встроенной обфускации — работает ли прокси обфускации (пропускается для Kernel и там, где NDMS обфусцирует сам) |
| PingCheck статус | состояние [мониторинга](../../monitoring/): связь есть или идёт восстановление (с номером рестарта) |
| Reverse path filter | значение `rp_filter`: при `1` (строгий режим) ответы через туннель могут отбрасываться — ошибка с командой исправления; `0` и `2` — норма |
| DNS leak проверка | DNS-серверы туннеля доступны через туннель, а не через WAN (только при полном прогоне; пропускается, если DNS туннеля публичные) |

## Sing-box-туннели и подписки

| Проверка | Что проверяет |
|---|---|
| Состояние туннеля | туннель запущен (для подписки — какой участник сейчас активен) |
| Proxy port (TCP) | локальный порт прокси sing-box принимает соединения |
| HTTP-check (gstatic) | запрос через прокси проходит |
| Задержка (RTT) | время ответа через прокси |
| Alt-check (Cloudflare) | контрольный запрос к другому сервису — отличает проблему туннеля от проблемы одного сайта |

## Restart-цикл

Тумблер **Включая restart-цикл** в расширенных параметрах добавляет к полному прогону проверку «Цикл Stop -> Start»: каждый запущенный туннель кратко перезапускается (на 2–5 секунд) и ждёт нового рукопожатия до 15 секунд. На это время связь через туннель прерывается. Для NativeWG-туннелей проверка пропускается.

## Отчёт и инцидент

- **Отчёт** — скачать полный JSON-отчёт (`diagnostics.json`) последнего прогона.
- **Инцидент** — подготовить сообщение о проблеме: окно напоминает, что awg-manager — open-source проект без SLA, а issue на GitHub публичный, поэтому перед отправкой уберите из отчёта ключи и адреса. Кнопка **Скачать и открыть GitHub** скачивает отчёт, копирует в буфер обмена заготовку текста issue и открывает страницу нового issue: вставьте текст и приложите скачанный файл вручную. Если проверки ещё не запускались, окно попросит сначала выполнить диагностику.

Что ещё приложить к issue — см. [Вопросы и решения](../../../faq/#как-сообщить-о-проблеме).
